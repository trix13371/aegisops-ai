# Границы безопасности S0-01

Активы: локальные credentials БД, код прототипа, записи аудита. Приложение
не имеет production-доступа, shell или LLM-инструментов. S0-03 добавляет
короткоживущий токен read-only локального ServiceAccount.
До соответствующего gate в прототип не передаются реальные данные.

Доверенные компоненты: пользователь компьютера, разработческие скрипты,
bootstrap/owner роли локальной БД. App — отдельная роль с SELECT/INSERT.
DPAPI-ключ OpenRouter находится вне этого репозитория. Персональный launcher
может передать его приложению в окружении дочернего процесса для явного
платного анализа. Разработческие модели получают только код прототипа.

Механизмы текущего среза:

- Allowlist URL и запрет query-параметров защищают CLI от произвольного назначения.
- Ошибки конфигурации и драйвера нормализуются; цепочки исключений подавляются.
- Проверка doctor читает текущие права, membership, владельцев, миграцию.
- SQL permissions запрещают UPDATE/DELETE/TRUNCATE/DDL/SET ROLE приложению.
- Ruff, import-linter и AST-тесты ограничивают выполнение команд в src.
- Gitignore, gitleaks и pip-audit поддерживают гигиену репозитория.
- .env не интерпретируется как код; случайные пароли не выводятся скриптами.

Это не ОС-песочница: процесс той же учётной записи может прочесть локальные
файлы, менять код и получить owner credentials. Администратор БД может изменить
аудит. Проверки не заменяют RBAC, Kubernetes admission, подписанные политики,
санитизацию контекста, SPIFFE/Vault или аудит-grade хранилище последующих этапов.

S0-02 добавляет Pydantic AuditRecord, Literal[False], ограничения коллекций,
точные boolean-поля, явные enum и сверку ссылок ID/evidence. Draft DTO не
принимают поля безопасности; связывание выполняет приложение. Валидация
данных не является санитизацией: фильтрация логов реализуется в S0-05.
Схема БД payload_json остаётся JSONB; записи через AuditStore будут обязательно
валидироваться в S0-07. Никакие поля JSON не исполняются.

Fixtures содержат недоверенную инструкцию и фейковую canary. CLI не отображает
их сырые логи. В S0-02 данные не передаются модели. JSON/YAML загружаются
с ограничением размера; duplicate keys, YAML aliases и Python tags запрещены.
Проверяется containment и symlink в компонентах пути. Это не защита от
конкурентной замены файлов другим процессом той же доверенной учётной записи.
readonly dict защищает от обычной мутации, не от враждебного Python-кода:
model_construct, model_copy и object.__setattr__ не являются входным API LLM.

S0-03 проверяет фиксированный kubeconfig без auth plugins, TLS CA и регистрацию.
JWT claims проверяются структурно; подпись проверяет apiserver. HTTP wrapper
блокирует non-GET, произвольные пути/origin и redirects. RBAC остаётся главным
барьером; live-тесты получили HTTP403. SecretStr скрывает токен в repr;
сообщения не включают ответы/headers SDK. Namespace marker имеет ограниченное
cluster-scoped право по ADR-005.

Приложение не обновляет токен автоматически. Отсутствие credentials, TTL,
marker или CA mismatch приводит к отказу. Проверки не защищают от владельца
хоста, произвольного туннеля или hostile Python. Данные runtime Kubernetes
ещё не передаются LLM или аудиту.

S0-04 нормализует только разрешённые metadata/status поля. Полный spec, env,
annotations и labels не читаются нормализатором и не входят в DTO. SDK получает
ответ apiserver с Pod, но сырой объект не сериализуется и не сохраняется.
Events ограничены UID/namespace; объём и страницы ограничены. Ошибки чтения
не превращаются в частичный успешный результат. Исключение — отсутствие
необязательного log stream (400/404 после успешной проверки маркера).
Сырые тексты остаются внутри процесса; CLI observe выводит только счётчики.
Сырые снапшоты нельзя передавать в LLM, БД или печатать целиком.

S0-05 очищает текст до включения в Incident и DiagnosisContext. Credentials
распознаются по известным формам и именам полей; redaction не гарантирует
удаление неизвестных или закодированных значений. Сначала очищается полный
ограниченный текст, затем применяется обрезка и деление на evidence.
ContextBuilder повторно проверяет данные, сохраняет ссылки и лимиты, отказывает
при credential-shaped ID или распознаваемом секрете между цитатами.
Невалидные DTO проверяются до сериализации, чтобы сообщения Pydantic не
выводили исходные данные. CLI вычисляет очищенный результат до печати.

Все evidence помечены untrusted=true. Prompt injection сохраняется как текст,
не формирует параметры исполнения. Санитизация сама по себе не защищает будущую
модель от следования инструкциям: разделение prompt/data и проверка рекомендаций
должны быть реализованы в S0-06/07. Проверки канареек сейчас покрывают Incident,
Context, их JSON и CLI; реальные границы LLM-запроса и payload_json будут
проверены в S0-06/07, как описано ниже.

Текущий срез S0-06/07 передаёт модели только очищенный размеченный контекст
synthetic/local-kind; tools отсутствуют, сетевой адрес/креденшелы ограничены
адаптером. Вывод валидируется, ссылки и каталог проверяются. Промпт сам по себе
не защита от injection; реальные полномочия отсутствуют. Transport ошибки
нормализованы, TLS проверяется, локальный endpoint не получает внешний ключ.

Policy и dry-run отделены import-linter от сервисов и LLM. Решение привязано
хешем к точным входам, шаблон пересчитывается перед аудитом. Это не подпись.
Аудит очищает весь record, проверяет контекст и производные значения, затем
выполняет INSERT без SQL echo/параметров в логах. Канарейка проверена в
фактическом HTTP-теле, выводе CLI и сохранённом payload_json. Искусственный
отказ INSERT не даёт успешного CLI-результата. Изменения данных/политик и
любое исполнение по-прежнему недоступны приложению.

S0-08 повторно валидирует весь source-батч и происхождение до анализа,
сохраняет ранние отказ/ошибку и успешное наблюдение без инцидентов. Никакие
исходные исключения источника не попадают в аудит. Ошибка первой или поздней
записи не выдаёт успешного итога батча; прежние транзакции могут сохраниться.
Audit show ограничивает объём, UUID и структуру и очищает исторический record;
сохранённые решения не исполняются/переоцениваются при чтении. Ручные policy
probes в eval не являются доказательством устойчивости настоящей модели.

F01 добавляет чистую версионируемую политику маршрутизации. Synthetic имеет
минимум public, local-kind — internal; доверенная конфигурация может только
повысить класс. OpenRouter получает только public, локальная модель —
public/internal/confidential, restricted не передаётся никакому клиенту модели.
Проверка стоит перед резервом бюджета и повторяется внутри HTTP/fake-клиента.
Отказ не вызывает сеть/модель; причина, версия и класс сохраняются в LLMMetadata.
Явный повышенный класс включён в хеш запроса и не читается из логов.

Это не DLP, гарантия zero-retention, data residency или изоляция loopback.
Restricted ограничивает передачу модели, но не детерминированный разбор и
локальное хранение аудита. Нельзя маркировать реальные данные synthetic,
а локальный URL может вести в туннель. Разрешение реальных данных и требования
хранения остаются отдельными решениями G(−1). Подробности — ADR-010.

F02 принимает ограниченную оценку через отдельный CLI. Привязку к сохранённой
рекомендации (run ID, recommendation ID/hash и origin) формирует серверный код,
не пользователь/модель. Вход валидируется до запросов, комментарий очищается
перед INSERT и при чтении. Ошибки не содержат исходный комментарий или SQL.
Записи и исправления append-only; unique/FK ограничения предотвращают второй
корень, ветвление, исправление чужого run/reviewer и конкурентную перезапись.
Doctor контролирует владельцев и SELECT/INSERT-only права обеих таблиц.

Reviewer остаётся неподтверждённым локальным псевдонимом: авторство и права
SRE не доказаны. Отзывы не предоставляют полномочий, не повышают автономность,
не меняют политики и не передаются LLM. Сводка мнений не является метрикой
качества на независимых инцидентах; локальная БД содержит тестовые отзывы.
При полной компрометации хоста/владельца БД история не защищена подписью/WORM.
Свободный текст может содержать нераспознанные PII/секреты, а shell history
не очищается приложением. Подробнее — ADR-011.

F03 добавляет заявленные пользователем причину/исход и ограниченный reference ID.
Reference обязателен для разметки, но не подтверждает факты/авторство источника;
URL не запрашивается и разметка не отправляется модели. SQL constraints и DTO
отвергают неизвестные категории, unknown-причину и разметку без ссылки.
При сравнении повторно проверяются run/origin/ID/hash рекомендации. Противоречия,
отсутствующая/неполная разметка и неизвестные диагнозы не становятся совпадениями.

Report читает bounded current heads в read-only REPEATABLE READ транзакции,
обнаруживает обрезанные группы и не печатает комментарии. Дедупликация действует
по существующему incident ID с временным окном, не доказывает независимость
кейсов. Fixtures/fallback и ответы модели различаются по метаданным аудита.
Отчёт не подтверждает качество настоящей модели, причинность исхода, MTTR
или gate; в локальной БД по-прежнему есть автоматические тестовые labels.
Подробнее — ADR-012.

F04 добавляет только public учебные runbook из фиксированного Git-каталога.
Они загружаются с ограничениями схемы/байтов/путей, secret-shaped строки
отвергаются. Выбор основан на очищенном pod_status, не на инструкциях в логах.
Справочный текст находится в недоверенном JSON, не даёт полномочий и не
добавляется в observation evidence. Недопустимая ссылка на runbook вместо
evidence приводит к fallback. Версии/хеши выбранных документов связаны с
prompt hash и сохраняются в прежнем JSONB без миграции.

Это не подпись или автоматическая проверка ревью Git, не защита от владельца
хоста и не доказанная устойчивость LLM к injection. Метка public должна
соответствовать содержимому; неизвестные формы секретов/PII могут не распознаться.
Internal runbook пока не поддержаны, чтобы не передавать их внешнему API
под классом учебной синтетики. Уровень остаётся L0. Подробнее — ADR-013.

F06 добавляет локально подписанные снимки audit_runs: публичный проверяющий
код в приложении, отдельный developer signer, ключ вне репозитория/БД (Windows
DPAPI текущего пользователя, POSIX 0600). Trust/HEAD/checkpoints вне БД доверены.
Проверяется raw физическая строка, подпись и цепочка; подмена/удаление защищённых
строк обнаруживаются, новые отмечаются unanchored с ненулевым exit. Верификатор
не очищает строки повторно и не может выпускать подписи. При сбое публикации
до атомарной замены HEAD старый anchor остаётся действующим; orphan не доверяется.

Это защита относительно ручной точки фиксации от изменений БД, не защита от
владельца ОС и не аудит-grade WORM/KMS. Первый снимок не подтверждает прошлую
подлинность. Неподписанные новые строки и изменения с восстановлением между
проверками не покрыты. Feedback-таблица не входит в снимок. Ротация ключей/архива,
удалённая фиксация и разделение identity signer/app — отдельные будущие работы.
Подробности — ADR-015; прежние оговорки выше относятся к прежним срезам.

F07 требует detached Ed25519 manifest для OPA-режима: хеши Rego/API guard/catalog,
revision и TTL до 24 часов, отдельный операторский policy key вне репозитория.
PEP проверяет подпись/content/floor/revocation/time до и после PDP. При смене
state или времени назад допуск отменяется. V2 receipt хранит проверяемые
относительно прошлого времени публичные доказательства; старый v1 аудит читается.

State/trust — доверенные локальные файлы, приложение их не меняет. Сам state
не подписан и не защищён аппаратным monotonic counter: откат ОС/файлов/часов
доверенным пользователем не покрыт. Нет нативного OPA bundle signing, удалённого
revocation feed, KMS/HSM, four-eyes или workload identity. Подписанный manifest
не доказывает подлинность процесса на loopback. Legacy Python mode остаётся
явным offline-треком без F07; исполнения нет. Подробнее — ADR-016.

F08 закрывает подмену loopback PDP: только TLS 1.3 с отдельным pinned CA,
проверкой IP SAN и точного server certificate до передачи проекции. OPA требует
clientAuth и точный subject PEP; посторонний клиент того же CA не получает доступ.
Истечение/смена публичного trust во время ответа отменяет результат.
Транспорт не переходит на HTTP, системные CA или другой endpoint.

TLS-ключи вне Git и защищены ACL/0600, но native PEM не зашифрован и процессы
работают под одним пользователем. Компрометация этого пользователя, часов или
операторского trust вне модели защиты. Это не SPIFFE/SPIRE/workload attestation.
Старые receipts не получают задним числом доказательство mTLS. Подробнее — ADR-017.

F09 отделяет collector от Control Plane по процессам, environment и импортам.
Подпись Ed25519 связывает содержимое пакета с закреплённым collector и регистрацией
локального kind. Фиксированные origin/internal, TTL, лимиты и повторная проверка
санитизации не позволяют пакету выбрать внешнего провайдера или чужой кластер.
Исторический replay не вызывает модель/OPA и не создаёт новые записи. Exclusive
claim закрывает повторный анализ при гонке/неопределённом исходе, ценой ручной
сверки после сбоя. Гарантия не распространяется на откат/удаление spool оператором.

Новый spool содержит очищенные, но internal наблюдения; универсального обнаружения
секретов нет. Приватный ключ и настройки роли не передаются через JSON. Процессы
работают под одним пользователем и сохраняют его файловые полномочия: очистка
environment/import-контракты не мешают захваченному коду прочитать чужой файл.
Не защищены враждебные файловые TOCTOU-гонки, компрометация host/trust/часов или
потеря питания. Receipt/claim не подписаны; F06 защищает только связанные строки
audit_runs после checkpoint. Сетевого приёмника и удалённой аттестации нет.
Ограничения и семантика неоднозначного результата — ADR-018.

UI02 добавляет доступ к папке только после явной регистрации её пользователем
через локальную сессию UI01. Источники не исполняются/импортируются; абсолютный
локальный путь, запрет symlink/junction обхода и проверка identity root ограничивают
случайный выход из выбранной области. Лимиты и SafeLoader без aliases ограничивают
объём разбора; partial не показывается как полный успех. Отчёт содержит имена
файлов/номера строк/фиксированные сообщения, без исходников и parser exception text.

Это не OS sandbox и не защита от владельца файловой системы: hostile TOCTOU,
неизвестные секретные имена, подмена всего приватного реестра доверенным пользователем
и потеря питания вне гарантий. Scanner не является универсальным распознавателем
секретов или SAST. Project reports не подписаны и не входят в F06 снимок аудита.
Новый import-контракт запрещает модулю projects выполнение команд, сеть, SDK,
LLM и DB/config. См. ADR-020.

UI04 добавляет отдельный разрешаемый оператором экспорт project-summary-v1 в
OpenRouter: только enum-коды/статусы/версии и ограниченные счётчики. Произвольные
строки, имена, пути, исходники и значения исключены структурой DTO, а не поиском
секретов по шаблону. Состав JSON виден перед отдельным согласием на платный запрос.
Это раскрытие производной сводки, не понижение класса исходников; F01 для
Kubernetes-телеметрии не меняется. Новые 18-й/19-й import-контракты отделяют
проекцию/состояние от транспорта и транспорт от incident/source сервисов.

Ответ модели недоверенный: enum-коды только из переданной сводки, bounded text,
неизвестные поля/tools/refusal/обрезанные ответы отвергаются. textContent исключает
HTML-интерпретацию, исполнение и автоматическое исправление отсутствуют. Claim
и worker-start с O_EXCL ограничивают один отчёт одной попыткой, включая сбои и
перезапуск. При неопределённости ответ не объявляется успешным и не повторяется.
Отдельный runtime-ключ, preflight общего лимита, verified TLS/CONNECT, запрет
redirects, лимиты входа/выхода и deadline сохраняются. История без подписи лежит
в .local/project-ai, вне F06; гарантии trusted filesystem и ограничения UI02
сохраняются. Данные провайдера/ключи не логируются. См. ADR-022.
