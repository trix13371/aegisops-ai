# ADR-007 — единый ограниченный запрос анализа

Принято: 15 октября 2026. Локальный прототип S0-06, часть B.11.

Диагноз и рекомендация требуют одного очищенного контекста и каталога. Для
небольшого бюджета AnalysisEngine запрашивает их одним JSON AnalysisDraft,
сохраняя раздельные DiagnosisDraft и RecommendationDraft внутри. Отдельные
генеративные DiagnosisEngine/RecommendationEngine сейчас не нужны.

JSON mode — подсказка формата провайдеру; доверие возникает только после
локальной Pydantic-валидации, повторной санитизации и проверки evidence,
каталога и целевого workload. Серверная поддержка строгой JSON Schema не
предполагается. Tools/functions отсутствуют. ID, обратимость и поля безопасности
назначаются приложением. Текст ответа не превращается в команды.

На инцидент разрешены две попытки, на серию — общий консервативный RunBudget.
Ошибка рекомендации не отбрасывает отдельно проверенный диагноз: после второй
попытки он может использоваться RuleBasedRecommender. Без валидного диагноза
создаётся unknown и предлагается передача человеку. Невалидный вход приложения
прерывает анализ до провайдера. Резерв бюджета не возвращается; фактический
usage отмечается неполным после транспортной ошибки.

Fake — стандартный режим CLI и CI. Ответы привязаны к хешу полного промпта,
а не только scenario_id. Учебные фикстуры проверяют механику, не качество модели.
Платные live-тесты требуют отдельного включения и ключа в окружении процесса.

Транспорт допускает фиксированный OpenRouter HTTPS или буквальный loopback
с явным портом. Ключи раздельны; TLS проверяется, redirects запрещены,
ошибки не раскрывают запрос. CONNECT proxy допустим только для OpenRouter;
DNS ограничен возможностями ОС. Произвольный внешний URL не поддерживается.

Анализ не присваивает status полного запуска и не пишет аудит. Это граница
S0-07; решение не меняет L0 и запрет исполнения ADR-003.
