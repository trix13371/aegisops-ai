# ADR-015 — подписанные снимки истории аудита

Принято 15 октября 2026. F06, локальный срез п. 4.4 плана Foundation & Safety.

История `audit_runs` сохраняется без перезаписи и миграции. Оператор выпускает
подписанные снимки через отдельный developer script. Каждый снимок содержит
UUID и SHA-256 всех физических строк, упорядоченных по UUID. Хеш охватывает
payload_json и все SQL-поля, включая метаданные и created_at. Перед хешированием
нет redaction, реконструкции DTO или повторного решения политики: иначе
проверка могла бы скрыть подмену. Невалидные исторические DTO можно зафиксировать
как байтовое состояние, но подпись не делает их валидными решениями.

Канонизация: UTF-8 JSON, sort_keys, компактные разделители, ensure_ascii=False,
allow_nan=False; SQL datetime преобразуются в UTC ISO с микросекундами, UUID —
в стандартную строку. Это протокол Python/PostgreSQL v1, не RFC 8785/JCS.
Домены row/link/signed-checkpoint и signing bytes различаются. Внутри снимка
каждое звено включает chain_id, индекс, run_id, row_hash и prev_hash. Первое
звено связано с хешем предыдущего подписанного снимка (либо нулём для genesis).

Тело подписывает Ed25519 из библиотеки cryptography; приложение содержит только
публичную проверку. API сверено с [документацией Ed25519](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).
Приватный ключ находится вне репозитория и БД: `work/audit-signing/`.
На Windows он защищён DPAPI текущего пользователя без UI/machine-wide flag;
на POSIX — файл 0600 с проверкой владельца. Это не KMS/HSM и не разделение
учётных записей: процесс того же доверенного пользователя может получить ключ.

Публичный trust.json, HEAD.json и checkpoints живут в `.local/audit-integrity/`,
вне БД и Git. Trust/key/HEAD — доверенные локальные файлы оператора. Из снимка
нельзя выбрать новый ключ или передать URL/path. HEAD закрепляет hash и UUID
последнего снимка; checkpoint-файл назван его хешем. Проверяются подписи, цепочки,
монотонность времени, сохранность всех прежних строк и все предыдущие снимки.
Откат только БД или подстановка старого checkpoint при сохранённом HEAD заметны.
Одновременный откат/подмена доверенных файлов хоста этой моделью не покрывается.

Публикация: один оператор, exclusive lock без автоматического захвата stale lock;
сначала проверка прежнего снимка против текущего состояния, затем новый файл
через exclusive create/flush/fsync, полная проверка нового архива, затем атомарная
замена HEAD. При ошибке до замены прежний HEAD остаётся действующим. Может
остаться orphan checkpoint: он не становится доверенным автоматически. Это
не распределённая транзакция и не гарантия переживания любой потери питания/FS.

`audit verify` только читает и возвращает:

- verified, exit 0: все текущие строки покрыты и совпадают;
- unanchored, exit 1: прежние строки совпадают, появились неподписанные новые;
- failed, exit 1: защищённые строки изменены или удалены;
- фиксированную ошибку, exit 1: нет доверенного снимка, неверная подпись,
  повреждены файлы/цепочка, ошибка БД или превышены лимиты.

Чтение БД — REPEATABLE READ READ ONLY, statement timeout 10 секунд. Максимум
10 000 строк и 64 MiB канонических данных; payload >1 MiB отклоняется SQL CASE
до передачи клиенту. Checkpoint ≤4 MiB; архив ≤64 снимков и 32 MiB. Превышение
не превращается в частичный успех и не продвигает HEAD. Ротация/архивирование
длинной истории и ключей требуют отдельного протокола; обрезка цепочки запрещена.

Гранулярность защиты — ручной снимок, не каждая транзакция append. Первый снимок
фиксирует текущее состояние и не доказывает отсутствие прошлой подмены. Новые
строки до следующего снимка и изменения, сделанные и отменённые между проверками,
не защищены. Приложение не может автоматически подписать/подтвердить свой вывод.
`recommendation_feedback` пока не покрыта этим протоколом. Нет WORM/transparency
log, KMS, защищённого времени или защиты от владельца хоста; это не завершение
п. 4.4 production-плана, MVP-A или переход с L0.
