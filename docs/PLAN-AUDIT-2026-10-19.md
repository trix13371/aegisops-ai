# Сверка с планом Stage −1, редакция 2.1

Дата: 19 октября 2026. Проверенный коммит: `42868c7`.
Основание: пользовательский файл `AegisOps_AI_Stage_m1_review_and_fixed (3).md`,
части A и B. Документ рассматривался как требования для сравнения, а не как

Исправления по этому историческому срезу перечислены отдельно в

к моменту аудита; они не переписаны задним числом после исправлений.

## Итог

Код всех восьми задач S0-01…S0-08 реализован; в репозитории есть исторические
результаты живой приёмки PostgreSQL/kind/OPA. Свежие офлайн-проверки успешны.
Однако повторную живую приёмку сейчас нельзя считать пройденной: PostgreSQL
остановлен. Это отдельный текущий блокер среды, а не отсутствие реализации БД.

Файл описывает локальный L0-прототип Kubernetes-конвейера. Это **не план всего
Этапа 1 Control Plane & Safe Execution**. Интерфейс, проверка пользовательского
кода и Docker-тесты — последующие расширения по запросам пользователя.
Foundation F01…F09 добавляет отдельные механизмы безопасности, но также не
означает завершения всего Этапа 1 или готовности к размещению в интернете.

продукту без уточнения: Kubernetes-ядро остаётся L0, а отдельный runner исполняет
выбранные проверки пользовательского кода в контейнере после согласия.

из исходного большого плана.

## Что поправить в первую очередь

### 1. P1, состояние среды: восстановить доступность PostgreSQL

Фактические результаты аудита:

- `doctor` и `doctor --source local-kind`: exit 1, безопасная ошибка БД `query error`.
- `alembic check`: connection timeout, успешная проверка схемы не получена.
- Docker показывает `aegisops-prototype-s001-postgres-1` в состоянии Exited,
  при этом kind-контейнер работает.

Ближайшая работа: штатно запустить существующую БД, проверить доступ/миграции
и read-only doctor; затем отдельным прогоном повторить живую приёмку.
Не пересоздавать БД и не удалять volume ради устранения ошибки.
Улучшить диагностику старта: явно показывать недоступный PostgreSQL и отличать
работающие локальные проверки проектов от недоступного Kubernetes/audit-трека.
В этом аудите контейнеры не запускались/не останавливались, данные не менялись.

### 2. P2, дефект контекста: учитывать имена в Python ImportFrom

Место: [context.py:148](../src/aegisops/project_code/context.py#L148), `_python_meta`.
Для `from . import helper` в `pkg/main.py` вычисляются кандидаты `pkg.py`
и `pkg/__init__.py`, но пропускается `pkg/helper.py`: `node.names` не используется.
То же ограничивает `from pkg import helper`, если helper — отдельный модуль.
В результате карта и подбор могут не добавить важный связанный файл.

Исправление: учитывать кандидаты импортируемых подмодулей с проверкой существующих
путей; сохранить ограничения, дедупликацию и различие модулей/символов.
Добавить регрессию для относительного и абсолютного ImportFrom, вложенных
пакетов и импорта обычного символа. Проблема не в вычислении `level-1`:
оно корректно для `from .helper import run`.

### 3. P2, проверка регрессий: подключить UI-тесты в CI

В [.github/workflows/checks.yml](../.github/workflows/checks.yml) и kind workflow
нет запуска `node --test tests/ui/dashboard-flow.test.cjs` и настройки Node.
Локально проходят 47 тестов, но они не защищают pull request автоматически.
Добавить отдельный CI-шаг с фиксированной поддерживаемой версией Node;
сохранить Python/kind/OPA-проверки. Это пробел CI, не ошибка Python-логики.

### 4. P2, качество контекста: улучшить охват больших проектов

Каталог ограничен 200 именами и строится через `os.scandir`/LIFO;
сортировка выполняется после усечения. Карта рассматривает первые 80 имён.
Лимиты нужны, но попадание файлов в ограниченный каталог зависит от обхода;
последующее ранжирование не возвращает пропущенные entrypoints и тесты.

Настоящий локальный GET для зарегистрированного AegisOps вернул `partial=true`,
четыре файла из project_ai и compose.yaml; среди них `__init__.py`, без тестов
и точки входа. Ошибки лимитов нет, предупреждение о неполноте есть, но это
слабый стартовый контекст для большого репозитория.

Улучшение: стабильный приоритетный обход кода/entrypoints/тестов/конфигурации,
справедливое распределение бюджета между каталогами и объяснения по фактическим
признакам. Не называть каждый запасной модуль «центральным», если нет входящих
связей. Не решать проблему простым снятием ограничений или отправкой всего кода.

### 5. P3, план и документация: уточнить действующие границы

Добавить явные ссылки из ранних ADR/threat model на поздние решения об исходниках
и runner; не переписывать старую историю приёмки как актуальные результаты.
Вести три отдельных списка: S0-прототип, локальная проверка проектов, дальнейший
серверный Control Plane. Не использовать количество тестов как процент готовности.

## Что добавить затем

1. Более полезную оценку AI: Python и JS/TS, несколько файлов, правильный код,
   реальные дефекты, ложные срабатывания и инъекции. Разметку проверяет человек.
   Измерять precision/recall, подтверждаемость замечаний и стоимость на задачу
   отдельно от валидности JSON/цитат. Текущий code-eval — три учебных примера,
   преимущественно Python, с совпадением строк/категорий.
2. Понятную готовность среды и единую повторяемую приёмку выбранного сценария:
   без БД, с БД, с Docker, с kind/OPA — отдельные результаты без ложного «всё готово».
3. Надёжность заданий: сценарии перезапуска/неопределённого результата, уборка
   оставшихся контейнеров и понятный статус. Сохранять запрет слепого retry.

Публичный хостинг пока отложен пользователем. К моменту размещения понадобятся
владельцы/права, серверная аутентификация, управляемая загрузка Git/архива,
постоянное хранилище/очередь, отдельный исполнитель, квоты, backup/restore,
секреты по ролям и новая приёмка изоляции. Это уже отражено в
[W01…W05](internet-deployment-roadmap.md), а не является недоделкой S0.
Сетевой Cluster Agent, lease/fencing и безопасное реальное исполнение действий
Kubernetes также нельзя считать реализованными по наличию локального OPA/spool.

## Свежая проверка и ограничения этого аудита

- Unit/contract/safety/E2E без live/integration: **1470 passed, 4 skipped**,
  154.21 s. E2E использует MemoryAuditStore. Артефакт вне Git:
  `.local/plan-audit-offline.xml`.
- UI MockDOM: **47 passed**.
- Ruff lint/format, mypy (**146 source files**), import-linter (**25 contracts**),
  **57 schemas** и package assets — успешно.
- Реальный локальный GET рекомендаций: HTTP 200, partial=true; ничего не
  отправлено runtime-модели, предпросмотр/задача не создавались.
- PostgreSQL/миграции: текущая проверка неуспешна. Live kind/OPA, чистая установка,
  новый платный runtime smoke, pip-audit и удалённый CI здесь не выполнялись.

Gemini через отдельный API разработки независимо просмотрел два ограниченных
набора исходников и уточнил выводы по дополнительным зависимостям. Оркестратор
проверял исходники, команды и воспроизведение. Четыре первоначальных подозрения
отклонены: fallback уже валидирует каталог через bind_recommendation; owner_kind
проставляется до создания evidence; level-1 корректен; `_exchange` уже направляет
запросы выбранному прямому провайдеру. Отдельный подтверждённый дефект — пропуск
ImportFrom aliases. Отсутствие UI-теста в CI остаётся пробелом проверки.
Модель не выполняла тесты и не получала ключи, `.env`, runtime-логи или исходники
пользовательских проектов.

Функционал, настройки, credentials и контейнеры в этом аудите не изменялись.
Добавлен только этот отчёт. Публикация в GitHub не выполнялась.
